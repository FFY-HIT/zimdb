构建 RSS 是 10 ms 采样的工具进程树同时驻留内存，可能重复计算共享页；观察器、共同同步辅助进程和多数文件页缓存不在此 RSS 中。共同 cgroup 上限为 116 GiB、swap=0。ZimDB 构建 cgroup 峰值（含文件页缓存）为 21.624 GiB，不能把 31.125 MiB RSS 说成总物理内存。PowerDNS 遇到 10,650 次 memory.max 事件，无 OOM，时延受该资源上限约束。

PowerDNS 按官方预签名 AXFR 部署语义存储：NSEC3/NSEC3PARAM 不作为普通 RR 直接物化，而是生成 NSEC3/ENT/索引并保留签名；索引已计入原生大小。接收、分类、物化耗时 1,636.490 秒；NSEC3/ENT/索引与 LMDB 插入、提交交织的阶段耗时 4,093.948 秒，后者不能称作纯 NSEC3 计算时间。普通源投影为 433,056,771 条。

DNSRocks 构建中转换、解析、调度耗时 2,150.957 秒，原生 sort/merge/SST/ingest 等耗时 338.338 秒。因此端到端构建优势不能全部归因于表示算法。

负载包括委派 A、委派下名称 A、含 DS 委派的 DS、不含 DS 委派的 DS、随机不存在名称 A，五类各 20,000 条。RD=0、DO=0、EDNS=1232，单个在途请求、一个有效工作线程、关闭响应缓存。服务器 CPU 亲和 2,4，客户端 6，观察器 0；每次启动前完整预读原生产物，再执行固定、独立的预热集。预读并不保证各系统相同的实际页缓存驻留量。

## 实现与原生配置

ZimDB 构造核心为 `218e9cd`，原生 `ZIMDNS1` 映像，Zstd、columnar 页、hierarchy 外排、body 元组、compact 名称键、分块 NS 池 65,536 项、上下文 NS 模板与 NSEC3 局部链接，2 个编码工作线程。无 owner 局部池；启用 front-code，COW 索引，构建声明内存参数 64 MiB、运行缓冲 4 MiB。

构造使用 SIMD parser，完整命令如下（路径替换为实际文件；输入已解压）：

```sh
make -C experiments/queryable_zone SIMDZONE_DIR=/path/to/pinned/simdzone
experiments/queryable_zone/native_zone build \
  --zone /path/to/com.zone --origin com. --out /path/to/image.zim --work /path/to/work \
  --memory-mib 64 --run-memory-mib 4 --codec zstd --pool none --front-code 1 \
  --index cow --key-codec compact --nsec3-next-key 0 --sort-engine hierarchy \
  --page-layout columnar --input-syntax simd --ns-pool-entries 65536 \
  --sort-tuple body --ns-templates 1 --nsec3-links 1 --encode-workers 2
```

RocksDB 为 9.11.2，采用 DNSRocks 原生默认 Snappy 和默认块参数，通过原生 builder/SST ingest 生成产物；本主表不是强制 Zstd + 64 KiB 再额外全量 compaction 的对照。PowerDNS 5.1.5 使用官方 auth-51 LMDB 预签名部署；BIND 9.20.30 通过 `named-compilezone -f text -F raw` 生成 raw、由 `named` 实际服务。

ZimDB 和 RocksDB 使用相同的 DNSRocks 权威处理控制流程。此 DNSRocks 是明确记录的实验控制分支，包含依赖升级、master-file 前端和可选存储接口；不能声称整个 daemon 是未经修改的上游。出处见 [UPSTREAM.json](../../adapters/dnsrocks/UPSTREAM.json)，部署见 [DNSRocks 集成说明](../../adapters/dnsrocks/README.zimdb.md)。查询读取器优化是工程改进，不作为表示算法创新。

测得 fast6 读取器 SHA-256：`1f06119cf0447b93f9ff7265b55de8bff4f2cae55783bea08075c9dfa6900c05`；测得云端 authority 二进制 SHA-256：`002667ab3b5a72eadd8f2fcd58ecf91f5a450ce0675e354498b1e96d276f2306`。发布时只调整 C++ 相对 include 和读取器 include shim，核心和读取器算法内容保持不变；本机构建的二进制受路径和工具链影响，不声称二进制相同。

## 结论与边界

相对本轮 DNSRocks 原生配置，ZimDB 原生体积缩小 2.752 倍，构建耗时约为 1/6.54；采样构建进程 RSS 明显更低，但这不等于总物理内存缩小相同比例。最新查询平均 RTT 约为 RocksDB 的 1.469 倍，查询采样 RSS 约为其 42.1%。

5 倍体积门槛仍未达到。查询时延也尚未优于 RocksDB。本轮没有四组完整 COM 的更新成本 W(Δ)，不作更新优势结论。此前其他压缩器的离线压缩结果不混入原生表示表。

数据仅支持这一个完整快照、固定均衡 DO=0 负载、每系统一次测量，不能推广为互联网平均查询时延、并发吞吐量或完整 DNSSEC 服务等价性。四组原生内容验收有对应记录；ZimDB 是与已独立完成 G1 的 R06 映像全文件 SHA-256 一致的传递验收，本轮没有重新遍历 441M 条 RR。源 DNSSEC 字节未为了性能删去。原生 RocksDB 在小型合成 ENT/通配边界仍有两项已知失败，原始失败保留；主 COM 五类负载全部通过，不据此称通用 KV 已解决完整名称语义。

发布前，本机构造与独立原生 G1/名称语义 fixture、Go 的 db/dnsserver 回归均通过。额外真实权威服务 smoke 为 8/9 通过：嵌套委派下查询被 DNSRocks 适配流程导向更深委派，而原生核心正确返回靠近 zone apex 的首个 zone cut。这一适配边界尚未修复，失败 wire 已保留在 `validation/SERVING_SMOKE.json`；它不在本轮 COM 五类负载中，不能将本次结果表述为权威服务所有语义均已通过。
